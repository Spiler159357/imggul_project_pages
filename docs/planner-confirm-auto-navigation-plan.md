# 플래너 개별 확정 후 자동 이동 계획

작성일: 2026-11-09

## 1. 목표와 이동 규칙

후보 검수 모달에서 `최종 선택 완료`로 현재 플랜을 확정하면 다음 순서로 처리한다.

1. 다음 플랜이 있으면 다음 플랜으로 이동한다.
2. 다음 플랜이 없고 이전 플랜이 있으면 이전 플랜으로 이동한다.
3. 양쪽 모두 없을 때 모달을 닫는다.

이동 대상은 기존 이전·다음 플랜 버튼과 동일하게 결정한다. 현재 화면의 카드 순서를 따르고, 검색·필터로 숨겨진 카드는 건너뛴다. 목록 끝에서 처음으로 순환하지 않는다.

`다음 플랜이 없음`은 현재 탐색 범위에 다음으로 표시되는 카드가 없다는 뜻이다. 다른 범위나 필터 밖의 플랜까지 탐색하지 않는다.

기존 버튼과 마찬가지로 이동 대상에 후보 이미지가 있으면 후보 검수 모달을, 후보가 없으면 플랜 편집 모달을 연다. 자동 이동을 위해 후보 있는 플랜만 따로 고르거나, 확정 이력이 있는 카드를 추가로 제외하지 않는다.

현재 `confirmPlannerSelection()`은 요청 실패 후 서버 재조회에서 항목이 사라진 경우에도 성공으로 복구한다. 이 판정을 유지하고, 최종 성공 여부가 정해진 뒤 자동 이동한다.

캐릭터/상황 기준은 가능한 조합의 카드를 표시하지만, `생성된 플랜 전체`는 저장된 항목만 표시한다. 따라서 확정 후 현재 카드가 남는 화면과 사라지는 화면을 모두 고려해야 한다.

## 3. 수정 흐름

### 3.1 확정 전에 이동 대상 저장

현재 검수 모달의 개별 확정인지 확인하고, 서버 요청이나 화면 갱신 전에 다음 정보를 저장한다.

- 원래 프로젝트 ID, 캐릭터 ID, 상황 ID
- 사용자가 닫거나 다른 플랜으로 이동했는지 확인할 작업 식별값
- `getPlannerWorkspaceNeighbor(1, characterId, situationId)` 결과
- `getPlannerWorkspaceNeighbor(-1, characterId, situationId)` 결과

실제 이동 대상은 `next ?? previous`로 선택한다. 대상은 `{ characterId, situationId }` 쌍으로 보관한다. 상황 기준 화면에서는 캐릭터가 달라질 수 있으므로 상황 ID만 저장하지 않는다.

확정 직전의 카드 순서와 필터 상태를 기준으로 삼는다. 확정 이후 재렌더링된 DOM에서 제거된 현재 카드를 다시 찾거나, 새 인덱스로 다음 카드를 계산하지 않는다.

### 3.2 기존 확정과 서버 동기화 수행

다음 처리를 유지한다.

- 중복 확정 방지와 확정 가능 여부 검사
- compact/legacy 확정 처리
- `retryPlannerReconciliation()`을 통한 최신 플랜·최종 이미지 재조회
- 서버 상태에 근거한 성공 복구
- 성공 항목의 생성 큐 정리와 비교 기준 정리
- 성공, 실패, 임시 후보 정리 실패 안내

서버 확정과 화면 동기화가 완료되어 개별 플랜의 성공이 확인된 경우에만 자동 이동한다. 이미지 미선택, 생성/예약 진행 중, 확정 실패 시에는 현재 검수와 선택을 유지한다.

### 3.3 성공 후 목적지를 직접 열기

`shouldCloseResultState` 하나로 모든 성공을 닫는 대신, 개별 확정의 후속 동작을 `이동`, `닫기`, `현재 화면 유지`로 구분한다.

1. 기존 확정 및 비교 기준 정리를 완료한다.
2. 원래 프로젝트와 검수 작업 문맥이 여전히 유효한지 확인한다.
3. 저장한 이동 대상이 있으면 공통 열기 경로로 연다.
4. 이동 대상이 없으면 `closePlannerResultModal()`로 닫는다.
5. 메인 목록은 기존 스크롤 유지 정책으로 갱신하고 확정 결과를 안내한다.

다음 후보 검수로 이동할 때는 현재 모달 ID를 먼저 `null`로 만들거나 빈 결과 오버레이를 렌더링하지 않는다. 새 대상의 조회가 완료된 뒤 ID를 교체하고 기존 `renderPlannerResultOverlay()`의 노드 갱신을 사용한다.

후보 없는 대상은 기존과 동일하게 편집으로 이동한다. 현재 `openPlannerWorkspaceItem()`은 검수를 닫은 뒤 편집 모달의 비동기 조회를 진행하므로, 필요한 데이터가 준비된 후 검수에서 편집으로 전환하도록 열기 순서를 보완한다.

## 4. 이동 코드와 비동기 처리 보완

### 4.1 수동·자동 이동의 열기 경로 공유

`navigatePlannerWorkspaceItem(offset)`는 기존처럼 이웃을 찾고, 자동 이동은 확정 전에 저장한 대상을 사용한다. 두 경우 모두 `openPlannerWorkspaceItem(situationId, characterId)`의 최신 조회와 모달 분기를 공유한다.

현재 `openPlannerWorkspaceItem()`은 오류를 내부에서 안내하고 반환값 없이 종료한다. 호출자가 이동 성공 여부를 구분할 수 있도록 `opened`, `cancelled`, `failed` 등 명시적인 결과를 반환하게 정리한다. 이동 실패를 확정 실패로 취급하거나 확정 API를 재실행하지 않는다.

### 4.2 처리 중 문맥 유지

- 확정 시작 즉시 처리 중 상태를 UI에 반영하고 이전·다음 플랜 이동을 일시 제한한다. `syncPlannerWorkspaceNavigation()`의 버튼 갱신과 실제 이동 함수의 방어 조건을 함께 맞춘다.
- 확정 및 자동 이동 중인 원래 검수는 백그라운드 갱신으로 항목이 제거되어도 중간에 빈 오버레이로 교체하지 않는다. 이 보호는 해당 확정 작업이 소유한 모달에만 적용한다.
- 닫기·Escape는 허용한다. 사용자가 닫거나 프로젝트/플랜 문맥을 변경하면 늦게 도착한 확정 결과가 모달을 다시 열지 않도록 기존 작업 식별값을 활용해 확인한다.
- 처리 잠금은 성공, 실패, 이동 취소를 포함한 모든 종료 경로에서 해제한다. 비교 이미지의 늦은 응답 차단과 편집 초안 처리는 기존 경로를 유지한다.

### 4.3 오류와 종료 처리

| 상황 | 처리 |
| --- | --- |
| 확정 실패 | 현재 후보 검수와 선택 유지, 오류 표시 |
| 요청 오류 후 서버 재조회에서 성공 복구 | 일반 성공과 동일하게 이동 |
| 확정 성공 후 서버 재조회가 끝내 실패 | 성공과 동기화 실패를 구분해 안내, 자동 이동 보류. 현재 데이터로 재확정을 유도하지 않음 |
| 확정 성공 후 대상 조회 실패 | 확정 성공은 유지. 검수 모달에서 이동 실패를 안내하고 저장된 대상으로 이동만 재시도할 수 있게 함 |
| 다음 대상 조회 실패 | 이를 다음 플랜 부재로 간주해 이전 플랜으로 이동하지 않음 |
| 다음·이전 대상 모두 없음 | 모달 닫기 및 포커스 복원 |
| 사용자가 처리 중 모달을 닫거나 프로젝트를 전환 | 원래 작업의 자동 이동 취소, 새 화면의 모달 상태를 덮어쓰지 않음 |

확정 성공 후 이동/동기화 오류를 표시하는 동안에는 이미 확정한 후보의 재확정 버튼을 비활성화한다. 대상 조회 재시도는 저장한 대상 ID를 사용하며 현재 카드가 남아 있다는 전제에 의존하지 않는다.

`confirmPlannerSelection()`의 `situationId = null` 일괄 처리 계약은 유지한다. 이번 자동 이동은 열려 있는 검수 모달의 해당 단일 플랜을 확정한 경우에 적용하고, 다른 호출까지 자동 이동으로 바꾸지 않는다.

## 7. 구현 순서

1. 공통 열기 함수에 명시적 결과와 데이터 준비 후 전환 경계를 마련한다.
2. 개별 확정 시작 시 기존 이웃 함수로 다음·이전 대상과 원래 작업 문맥을 저장한다.
3. 확정 성공 후 자동 이동 또는 정식 닫기를 적용하고 중간 오버레이 제거를 방지한다.
4. 처리 중 탐색 제한, 문맥 취소, 동기화/이동 실패 안내와 이동 재시도를 연결한다.
5. 문서·모듈 버전·정적 검사를 갱신한다.

## 8. 구현 반영

2026-11-09 위 흐름을 서비스 코드에 반영했다. `manage.js`의 프로젝트 목록·상세·섹션 진입에서도 진행 중인 모달 열기를 취소해, 화면 전환 후 늦은 응답이 원래 모달을 다시 열지 않도록 연결했다.

로컬에서는 JavaScript 구문, 플래너 소스 계약, 모듈 버전, diff 공백, UTF-8/BOM만 검사한다. 실제 동작 확인은 사용자 commit/push 후 위 표의 Cloudflare 확인 항목으로 진행한다.
