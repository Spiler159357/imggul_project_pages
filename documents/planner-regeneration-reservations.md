# 플래너 재생성 예약

작성일: 2026-11-08

## 동작 계약

- 프로젝트+캐릭터당 기존 run과 단일 activeJob을 유지한다. 플랜 복제는 하지 않는다.
- 완료된 상황의 후보는 같은 캐릭터의 다른 상황이 생성 중이어도 선택할 수 있다.
- 결과 화면의 다시 생성은 서버에 기존 item의 재생성 명령을 등록한다.
- 캐릭터에 활성 작업이 있으면 그 작업 전체가 끝난 뒤 FIFO 순서로 실행한다. 실행 중인 이미지나 상황을 선점하지 않는다.
- 기다리는 동안 후보와 선택을 유지한다. 실행 작업 전환 시 해당 item의 후보를 비우고 새 generationSequence를 부여한다.
- 예약 취소는 아직 실행되지 않은 명령만 제거한다. 실행 시작과 취소가 겹치면 revision 갱신에 먼저 성공한 작업이 우선한다.
- 실행·일시정지·취소 처리·예약이 남아 있는 캐릭터의 최종 확정은 서버에서도 금지한다. 편집·삭제·경로 변경 역시 제한한다.
- 후보 선택은 DB에 저장하지 않는다. 같은 페이지 세션에서 재조회·폴링·다른 플랜 이동 후 복원하며, 재생성으로 후보 세대가 바뀌면 해제한다. 페이지 새로고침을 넘는 선택 보존은 추가하지 않았다.

예: A/B/C 생성 중 A와 B 재생성을 예약하면 C까지 기존 작업을 끝낸 뒤 A, B 순서로 재생성한다. 재생성 A가 완료되고 B가 생성 중일 때 다시 A를 예약하면 B 다음에 동일한 A item을 다시 생성한다.

## 저장과 경쟁 처리

새 테이블·record type 없이 기존 run JSON에 다음 서버 소유 필드를 추가한다. 이전 레코드의 누락 필드는 빈 목록/false/null로 처리한다.

| 필드 | 역할 |
| --- | --- |
| pendingRegenerations | itemId, sourceGenerationSequence, requestId를 가진 FIFO 목록 |
| pendingCleanupKeys | 실행 전환으로 분리한 이전 세대 R2 후보 파일의 정리 목록 |
| regenerationPaused | 치명적 오류 후 예약의 자동 진행 중지 |
| confirmingOperation | 최종 확정과 생성 시작의 동시 실행 방지 |
| item.generationSequence | 후보가 0장이어도 해당 상황의 생성 세대 보존 |
| item.lastRegenerationRequestId | 실행으로 전환된 요청의 재전송 식별 |

예약 ID는 itemId와 요청 당시 generationSequence에서 결정적으로 만든다. 동일 요청은 대기/실행/완료 이후에도 중복 등록하지 않는다. 새로운 생성 결과를 보고 요청하면 다른 세대의 정상적인 후속 요청이 된다.

예약에는 플랜·설정을 복사하지 않는다. 원본 item의 생성 구조를 편집할 수 없도록 잠가 접수 당시 설정과 목표 장수를 보존한다. 일반 run 저장으로 후보·진행률·예약·정리 목록을 오래된 클라이언트 데이터로 덮어쓰지 않도록 서버 값을 보존한다.

정상 완료와 슬롯 재시도 소진에 의한 종료는 같은 optimistic UPDATE 안에서 첫 예약을 새 activeJob으로 전환한다. 예약 제거, 새 생성 세대, 기존 후보 분리, 다음 실행 포인터를 함께 반영한다. 최신 레코드를 재조회해 재적용하므로 예약 등록과 이미지 완료가 겹쳐도 한쪽을 유실하지 않는다.

R2 후보는 서버 전환이 확정된 뒤 정리한다. 정리 목록은 성공한 키만 제거한다. 큐 슬롯 준비 및 watchdog에서 재시도하며, 새 세대와 다른 상황의 키는 삭제하지 않는다. 원본 후보 삭제를 요청 전에 수행하는 클라이언트 경로는 결과 화면 재생성에서 제거한다.

새 작업 저장 후 Queue 전달이 실패해도 queued 상태가 남는다. 재생성 작업이 실행 claim 없이 5분 이상 기다리면 기존 watchdog이 재전달한다. NovelAI cooldown 중에는 이 조건으로 강제 전달하지 않는다. 기존 실행 lease 복구도 유지한다.

상태 응답은 revision이 더 오래되면 적용하지 않는다. 선택은 프로젝트/캐릭터/item별로 보관하고 해당 후보 세대와 키가 여전히 유효할 때만 복원한다.

## 제어와 확정

- 일시정지: 현재 작업을 멈추고 예약을 보존한다.
- 재개: 멈췄던 작업을 우선 재개한다. 치명적 오류로 예약이 멈춘 경우에는 첫 예약을 실행으로 전환한다.
- 전체 취소: 제어 대상 캐릭터의 예약을 함께 제거한다.
- 치명적 생성 오류: 남은 예약을 보존하고 paused로 표시한다. 사용자가 재개하거나 예약을 취소할 수 있다.
- 일부 슬롯의 재시도 소진: 현재 작업을 부분 실패/실패로 종료하고 다음 예약을 진행한다.
- 최종 확정: run revision 조건으로 확정 소유권을 확보한 뒤 R2 작업을 한다. 다른 탭의 생성 시작과 확정이 동시에 진행되지 않는다. 정상 확정 시 기존 commit에서 소유권을 함께 제거하며 실패 시 해제한다.
- 확정 처리 도중 Worker가 종료된 경우: 10분 lease가 지난 뒤 같은 후보를 선택하고 동일 확정을 재시도할 수 있다. 서로 다른 확정 요청으로 소유권을 대체하지 않는다.

## API

관리자 인증이 필요한 POST 경로다. 응답의 data는 최신 compact run이다.

- `/api/planner/compact/generate/regenerate`: runKey, itemId, sourceGenerationSequence. queued와 duplicate도 응답한다.
- `/api/planner/compact/generate/cancel-regeneration`: runKey, itemId, requestId. 이미 실행 중이면 409를 반환한다.

기존 status/batch status 응답에 예약 목록·예약 중지 여부를 포함하며 각 item에 regenerationReservation을 노출한다.

## 배포와 검증

DB migration은 없다. **Pages와 background Worker를 모두 같은 코드로 배포해야 한다.** background Worker가 예약 전환과 watchdog을 실행하므로 Pages 배포만으로는 기능이 완성되지 않는다. 기존 background 배포 명령은 `npm run deploy:background`다. 이 작업에서는 배포·커밋·푸시하지 않는다.

로컬은 구문·소스 정적 검사와 BOM 검사만 수행한다. 다음 항목의 실제 검증은 커밋/푸시 및 양쪽 Cloudflare 배포 이후 진행한다.

1. A 완료/B·C 진행 중 A 후보 선택. B·C 완료 후에도 A 선택이 유지되는지 확인한다.
2. 같은 시점에 A, B를 순서대로 재생성 예약. 기존 B·C가 끝난 뒤 A, B 순으로 실행되고 item 수/ID가 변하지 않는지 확인한다.
3. 재생성 A 완료/B 진행 중 A를 다시 예약. B 이후 A가 재실행되는지 확인한다.
4. 예약 중 후보와 선택 유지, 예약 취소 후 유지, 실제 재생성 시작 시 해당 상황의 선택 해제를 확인한다.
5. 두 탭의 같은 요청, 중복 클릭, 오래된 세대 요청, 응답 유실 후 재요청을 확인한다.
6. 예약 직후 창 닫기/새로고침, 일시정지/재개, 전체 취소를 확인한다.
7. 부분 실패는 다음 예약 진행, 인증/잔액 등 치명적 오류는 예약 정지 및 수동 재개를 확인한다.
8. 새 작업 저장 후 전달 실패는 watchdog으로 복구되고, 이전 후보 R2 삭제 실패는 다음 처리에서 재시도되는지 확인한다.
9. 실행/예약 중 확정 API 직접 요청이 409이고, 다른 캐릭터의 완료 플랜은 선택·확정 가능한지 확인한다.
10. Pages와 Worker의 로그에서 중복 count, 오래된 세대 후보 복원, 미정리 파일, 예상 밖 추가 생성이 없는지 확인한다.
