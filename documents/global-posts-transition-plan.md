# 게시글 전역화 전환 계획서

## 1. 목표

현재 게시글은 `guest_posts.project_id`와 프로젝트별 API·화면·R2 경로에 종속되어 있다. 이를 하나의 전역 게시글 컬렉션으로 전환한다.

전환 후의 기준 동작은 다음과 같다.

1. 관리자는 프로젝트 탭 첫 화면에서 프로젝트 목록과 별도의 `게시글 관리` 구역을 볼 수 있다.
2. 게시글 작성·수정·삭제와 댓글·대댓글 관리는 특정 프로젝트를 선택하지 않고 전역 게시글 관리 화면에서 수행한다.
3. 각 공개 프로젝트의 게스트 페이지에는 현재처럼 `게시글` 탭이 존재하지만, 어느 프로젝트에서 열어도 같은 전역 게시글 목록과 상세를 보여 준다.
4. 게시글·댓글·첨부 이미지는 프로젝트 이름 변경, 경로 변경, 공개 해제, 삭제의 영향을 받지 않는다.
5. 기존 게시글·댓글·첨부 이미지는 테스트 데이터이므로 이관하지 않고 삭제할 수 있다. 새 전역 구조에서 데이터를 다시 시작한다.

이번 작업은 게시글의 전역화에만 집중한다. 캐릭터·상황·플래너·프로젝트 공개 범위는 현재 프로젝트 종속 구조를 유지한다.

## 2. 현재 구조와 결합 지점

### 2.1 데이터와 저장소

- `migrations/0019_guest_posts_comments.sql`의 `guest_posts.project_id`는 `v2_projects.id`를 참조하고 `ON DELETE CASCADE`가 설정되어 있다.
- 목록 인덱스도 `(project_id, created_at DESC, id DESC)`를 기준으로 한다.
- 게시글 이미지는 `{projectPrefix}_guest_posts/{postId}/...` R2 key에 저장된다.
- 프로젝트 삭제 시 프로젝트 prefix 전체를 R2에서 지운 뒤 `v2_projects` 행을 삭제하므로, DB와 R2 모두 프로젝트 수명 주기에 묶여 있다.
- 프로젝트 경로 변경 시 `guest_posts.image_key`도 프로젝트 prefix에 맞춰 갱신된다.

### 2.2 서버 API

- 게스트 목록·상세·이미지·댓글 작성은 `/api/guest/projects/{projectPath}/posts...` 형태다.
- 관리자 목록·작성은 `/api/admin/projects/{projectId}/posts`를 사용한다.
- 게시글 조회와 변경 쿼리는 모두 `post_id + project_id` 소속 검사를 수행한다.
- 댓글 수정·삭제 가능 여부도 댓글 → 게시글 → 프로젝트 공개 상태 조인에 의존한다.
- 댓글 요청 제한 bucket은 `projectId + IP`를 기준으로 계산한다.

### 2.3 관리자 UI

- `public/js/project/shared.js`의 `PROJECT_SECTIONS` 안에 게시글이 프로젝트 섹션으로 등록되어 있다.
- `public/js/project/manage.js`는 프로젝트 상세 대시보드에 게시글 카드를 렌더링한다.
- `public/js/project/posts.js`는 활성 프로젝트와 `project.posts` 캐시에 의존하며 URL도 `#project/{projectId}/posts` 형태다.
- 뒤로 가기 복원 상태 역시 `projectId`, `projectSection: 'posts'`, `projectPostId`를 함께 저장한다.

### 2.4 게스트 UI

- 공개 페이지는 `/{projectPath}`에서 열리고 캐릭터와 게시글 탭을 제공한다.
- `public/js/guest.js`는 현재 프로젝트에서 만든 `apiBase` 아래로 게시글 요청을 보낸다.
- 화면 해시 `#posts`와 `#posts/{postId}`는 프로젝트 URL 내부 상태이므로, 이 부분은 전역화 후에도 그대로 유지할 수 있다.

## 3. 목표 아키텍처

### 3.1 소유권 원칙

게시글은 프로젝트의 자식 엔터티가 아니라 애플리케이션 전역 엔터티로 취급한다.

- 게시글의 정식 식별자는 `postId` 하나뿐이다.
- 게시글 조회·수정·삭제에 프로젝트 ID를 요구하지 않는다.
- 댓글은 게시글에만 속하고 대댓글은 해당 게시글의 최상위 댓글에 속한다.
- 프로젝트 공개 상태는 캐릭터·이미지 페이지 접근에만 적용하며 전역 게시글 자체의 생명 주기에는 관여하지 않는다.
- 모든 공개 프로젝트 게스트 페이지는 동일한 전역 게시글 API를 사용한다.

### 3.2 화면 구조

관리자 프로젝트 탭 첫 화면은 다음 두 구역으로 구성한다.

1. `프로젝트 목록`: 기존 프로젝트 생성·선택 기능을 유지한다.
2. `게시글 관리`: 전역 게시글 목록/작성 화면으로 이동하는 독립 카드 또는 버튼을 제공한다. 총 게시글 수와 최근 게시글 요약은 선택 사항이며, 초기 구현은 진입 버튼과 간단한 설명만 제공해 불필요한 초기 API 요청을 피한다.

프로젝트 상세 대시보드에서는 게시글 카드를 제거한다. 게시글 기능이 두 위치에 중복 노출되지 않게 한다.

관리자 라우트는 다음 형태를 권장한다.

- 목록/작성: `#project/posts`
- 상세/수정: `#project/posts/{postId}`

게스트 라우트는 기존 프로젝트 주소와 해시를 유지한다.

- `/{projectPath}#posts`
- `/{projectPath}#posts/{postId}`

따라서 게스트는 어느 프로젝트에서 진입했는지에 따라 캐릭터 화면으로 돌아갈 프로젝트 문맥은 유지하지만 게시글 내용은 모두 동일하게 본다.

## 4. 데이터 모델 전환

### 4.1 권장 스키마

`guest_posts`라는 테이블명은 유지하되 프로젝트 소유권을 완전히 제거한다.

권장 최종 컬럼은 다음과 같다.

| 컬럼 | 정책 |
| --- | --- |
| `id` | UUID 기본 키 |
| `title`, `body` | 게시글 제목과 본문 |
| `image_key` | 전역 R2 key를 저장 |
| `created_at`, `updated_at` | 서버가 생성한 작성·수정 시간 |

`project_id`, `source_project_id` 등 프로젝트를 나타내는 컬럼은 두지 않는다.

새 목록 인덱스는 다음 기준으로 바꾼다.

```sql
CREATE INDEX idx_guest_posts_created
ON guest_posts(created_at DESC, id DESC);
```

`guest_comments`에는 대댓글을 위한 `parent_comment_id TEXT NULL`을 추가한다.

- `post_id`는 `guest_posts.id`를 `ON DELETE CASCADE`로 참조한다.
- `parent_comment_id`는 같은 `guest_comments.id`를 `ON DELETE CASCADE`로 참조한다.
- 대댓글은 한 단계만 허용한다. 대댓글에 다시 답글을 다는 2단계 이상의 중첩은 서버에서 거절한다.
- 부모 댓글과 대댓글은 반드시 같은 `post_id`를 가져야 한다.
- 부모 댓글을 삭제하면 그 아래 대댓글도 함께 삭제한다.
- 목록 조회를 위해 `(post_id, parent_comment_id, created_at ASC, id ASC)` 인덱스를 둔다.
- `request_key` 중복 방지는 지금처럼 게시글 단위로 유지한다.

### 4.2 D1 마이그레이션 방식

기존 데이터 보존이 필요 없으므로 복사나 임시 테이블 없이 명확한 초기화 migration을 사용한다.

1. 외래키 순서에 맞춰 `guest_comments`를 먼저 삭제한다.
2. `guest_posts`를 삭제한다.
3. 기존 프로젝트 ID가 포함된 rate-limit bucket도 의미가 없으므로 `guest_comment_rate_limits`를 삭제한다.
4. 프로젝트 컬럼이 없는 `guest_posts`를 새로 만든다.
5. `parent_comment_id` self-reference가 포함된 `guest_comments`를 새로 만든다.
6. `guest_comment_rate_limits`와 전역 기준 인덱스를 다시 만든다.

이 migration은 기존 테스트 게시글·댓글을 의도적으로 삭제한다. 실행 전 데이터 export나 복구 절차는 이번 작업의 필수 범위가 아니다.

### 4.3 R2 이미지 경로

신규 전역 key 규칙은 다음과 같이 프로젝트 prefix 밖에 둔다.

```text
_guest_posts/{postId}/image-{uuid}.{ext}
```

`_guest_posts`는 이미 내부 프로젝트 폴더 제외 목록에 포함되어 있으므로 프로젝트 목록에 잘못 표시되지 않는다.

기존 `{projectPrefix}_guest_posts/` 객체는 이관하지 않는다. 새 서버 코드는 `_guest_posts/`만 읽고 쓴다. 기존 테스트 이미지 객체는 기능 전환과 별개로 나중에 일괄 삭제할 수 있으며, 남아 있어도 새 API에서는 참조되지 않는다.

## 5. API 개편

### 5.1 정식 API

| 용도 | 메서드와 경로 |
| --- | --- |
| 게스트 게시글 목록 | `GET /api/guest/posts?cursor=&limit=` |
| 게스트 게시글 상세 | `GET /api/guest/posts/{postId}` |
| 게스트 게시글 이미지 | `GET|HEAD /api/guest/posts/{postId}/image` |
| 게스트 댓글·대댓글 작성 | `POST /api/guest/posts/{postId}/comments` |
| 댓글·대댓글 수정/삭제 | `PATCH|DELETE /api/guest/comments/{commentId}` |
| 관리자 게시글 목록 | `GET /api/admin/posts?cursor=&limit=` |
| 관리자 게시글 작성 | `POST /api/admin/posts` |
| 관리자 상세·수정·삭제 | 기존 `GET|PATCH|DELETE /api/admin/posts/{postId}` 유지 |
| 관리자 이미지 조회 | 기존 `GET|HEAD /api/admin/posts/{postId}/image` 유지 |

목록·상세 쿼리에서는 `project_id` 조건과 프로젝트 조인을 제거한다. 게시글 이미지 URL도 전역 게스트 이미지 경로를 반환한다.

댓글 작성 body는 일반 댓글이면 `parentCommentId`를 생략하고, 대댓글이면 부모 댓글 ID를 담는다.

### 5.2 댓글·대댓글 정책

- `getCommentWithPost`는 프로젝트 조인과 `project_is_public` 검사를 제거한다.
- 일반 댓글과 대댓글 모두 작성자 이름, 비밀번호, 본문을 입력한다.
- 비관리자 수정·삭제는 해당 댓글 또는 대댓글을 작성할 때 설정한 비밀번호 검증을 요구한다.
- 대댓글 생성 시 서버는 부모 댓글이 존재하고 같은 게시글 소속이며 부모 자체가 최상위 댓글인지 확인한다.
- 존재하지 않는 부모, 다른 게시글의 부모, 대댓글을 부모로 지정한 요청은 400 또는 404로 거절한다.
- 상세 API는 최상위 댓글을 작성 순으로 반환하고 각 댓글의 `replies` 배열도 작성 순으로 반환한다.
- `commentCount`는 최상위 댓글과 대댓글을 모두 합한 수로 정의한다.
- 관리자 화면에서는 댓글과 대댓글을 모두 비밀번호 없이 삭제할 수 있다.
- 댓글 작성 요청 제한은 `global-posts + IP` 기준으로 계산한다. 프로젝트를 바꿔 제한을 우회할 수 없게 한다.
- 일반 댓글과 대댓글은 같은 요청 제한을 공유한다.
- 게시글 API는 프로젝트 공개 여부와 관계없이 동일한 전역 데이터를 반환한다.
- 프로젝트 게스트 HTML 자체는 지금처럼 공개 프로젝트에서만 열 수 있다. 별도의 전역 공개 게시글 전용 HTML 경로는 이번 범위에 추가하지 않는다.

### 5.3 구 API 제거

테스트 데이터와 이전 화면 호환이 필요하지 않으므로 프로젝트별 게시글 API는 새 전역 API 배포와 동시에 제거한다. 프로젝트 ID가 포함된 요청을 전역 요청으로 묵시적으로 변환하지 않는다. 잘못된 호출은 일관된 404 JSON을 반환해 남은 구 클라이언트 참조를 쉽게 발견할 수 있게 한다.

## 6. 관리자 UI 변경

### 6.1 프로젝트 첫 화면

`renderProjectManageShell`을 프로젝트 목록과 전역 도구 영역을 함께 렌더링하도록 변경한다.

- 상단 또는 프로젝트 목록 위에 `게시글 관리` 카드를 둔다.
- 카드 설명은 “모든 공개 프로젝트에 공통으로 표시되는 게시글을 관리합니다.”처럼 전역 범위를 명시한다.
- 프로젝트가 하나도 없어도 게시글 관리에는 접근할 수 있어야 한다.
- 프로젝트 목록의 로딩/오류가 게시글 관리 진입을 막지 않게 UI 상태를 분리한다.

### 6.2 프로젝트 상세

- `PROJECT_SECTIONS`에서 `posts` 항목을 제거한다.
- 프로젝트 상세 6칸 그리드를 5개 섹션에 맞게 조정한다.
- `renderProjectPanelItems`와 `openProjectSection`의 게시글 전용 분기를 제거한다.
- 프로젝트 객체의 `posts`, `postsLoaded` 캐시 필드를 제거한다.

### 6.3 전역 게시글 모듈

기존 `public/js/project/posts.js`의 편집 UI는 재사용하되 활성 프로젝트 의존성을 제거한다.

- 상태를 `window.GLOBAL_POSTS`, `window.GLOBAL_POSTS_LOADED`, `window.GLOBAL_ACTIVE_POST`처럼 전역 게시글 전용으로 분리하거나 모듈 내부 상태 객체로 캡슐화한다.
- 헤더의 뒤로 가기는 프로젝트 상세가 아니라 프로젝트 탭 첫 화면으로 이동한다.
- 제목 영역에는 프로젝트 이름 대신 `전역 게시글`을 표시한다.
- 목록·작성 요청은 전역 관리자 API를 사용한다.
- 저장·삭제 후 route state는 `projectView: 'global-posts'` 또는 `global-post-detail`을 사용한다.
- 댓글은 최상위 댓글 아래에 대댓글이 들여쓰기되어 보이도록 렌더링한다.
- 관리자 삭제 버튼은 댓글과 대댓글 각각에 제공한다. 부모 댓글 삭제 시 하위 대댓글도 함께 삭제된다는 확인 문구를 표시한다.
- 포커스 복원, 편집 중 자동 갱신 보호, 스크롤 보존 기능은 현재 동작을 유지한다.

## 7. 게스트 UI 변경

`public/guest.html`의 탭과 레이아웃은 유지한다. `public/js/guest.js`에서 게시글 요청 주소만 전역 API로 분리한다.

- 프로젝트 요약과 캐릭터 요청은 기존 `projectApiBase`를 사용한다.
- 게시글 목록·상세·이미지·댓글 요청은 `globalPostsApiBase = '/api/guest/posts'`를 사용한다.
- `#posts` 및 `#posts/{postId}` 해시와 목록 스크롤 복원은 유지한다.
- 프로젝트 A에서 작성된 글이라는 표현은 제거한다.
- 프로젝트마다 캐시된 별도 목록이 생기지 않도록 변경 감지와 새로고침도 전역 API만 호출한다.
- 각 최상위 댓글에 `답글` 버튼을 제공한다. 누르면 해당 댓글 바로 아래에 이름·비밀번호·본문 입력 폼을 연다.
- 한 번에 하나의 대댓글 작성 폼만 열고, 취소·작성 완료 뒤 원래 `답글` 버튼으로 포커스를 돌려준다.
- 대댓글에도 수정·삭제 버튼을 제공하며 기존 댓글 비밀번호 모달을 재사용한다.
- 모바일에서도 부모-자식 관계가 보이되 과도한 들여쓰기로 본문 폭이 좁아지지 않게 한 단계만 들여쓴다.

게시글 탭을 누르면 모든 공개 프로젝트에서 완전히 같은 목록 순서, 댓글·대댓글 수, 상세 내용이 보여야 한다.

## 8. 프로젝트 수명 주기 정리

전역화 후 프로젝트 작업은 게시글에 영향을 주지 않아야 한다.

### 프로젝트 삭제

- `DELETE FROM v2_projects`가 게시글을 cascade 삭제하지 않도록 DB 외래키를 제거한다.
- R2 게시글 이미지가 `_guest_posts/`에 있으므로 프로젝트 prefix 삭제에 포함되지 않는다.
- 기존 프로젝트 하위의 테스트 게시글 이미지는 이관 대상이 아니므로 프로젝트 삭제 시 함께 사라져도 된다.

### 프로젝트 경로 변경

- R2 프로젝트 폴더 이동 대상에서 전역 `_guest_posts/`는 자연스럽게 제외된다.
- `UPDATE guest_posts SET image_key = ... WHERE image_key LIKE oldPrefix` 배치를 제거한다.

### 프로젝트 공개 상태 변경

- 캐릭터 게스트 페이지 접근 여부만 바뀐다.
- 전역 게시글 데이터와 댓글·대댓글은 삭제·비공개 처리하지 않는다.

## 9. 구현 순서

### 1단계: 스키마 초기화

1. 새 D1 migration에서 기존 댓글·게시글·rate-limit 테이블을 삭제한다.
2. 프로젝트 외래키가 없는 전역 게시글 테이블을 만든다.
3. 한 단계 대댓글을 지원하는 self-reference 댓글 테이블과 인덱스를 만든다.
4. 전역 기준 rate-limit 테이블을 다시 만든다.

### 2단계: 서버 전역 API

1. 전역 API와 전역 쿼리를 추가한다.
2. 신규 이미지는 `_guest_posts/`에 저장하고 이 prefix만 조회한다.
3. 댓글 작성에서 선택적 `parentCommentId`를 검증한다.
4. 상세 응답을 최상위 댓글과 `replies` 배열 구조로 직렬화한다.
5. 프로젝트별 게시글 API를 제거한다.
6. 프로젝트 삭제·경로 변경 로직에서 게시글을 분리한다.

### 3단계: 관리자 UI 전환

1. 프로젝트 첫 화면에 전역 게시글 관리 진입 구역을 추가한다.
2. 게시글 모듈의 활성 프로젝트 의존성을 제거한다.
3. 관리자 라우트를 `#project/posts...`로 변경한다.
4. 프로젝트 상세의 게시글 카드를 제거한다.
5. history/popstate 복원 분기를 전역 게시글 상태에 맞춘다.

### 4단계: 게스트 UI 전환

1. 게시글 요청을 전역 API로 교체한다.
2. 여러 프로젝트 URL에서 같은 목록·상세·댓글을 공유하는지 확인한다.
3. 최상위 댓글 작성, 대댓글 작성, 각각의 수정·삭제를 연결한다.
4. 부모 댓글 삭제 시 대댓글 cascade와 화면 갱신을 확인한다.

### 5단계: 불필요한 기존 코드·객체 정리

1. 더 이상 사용하지 않는 프로젝트 게시글 캐시, 구 API 분기, rename 보정 로직을 제거한다.
2. 기존 `{projectPrefix}_guest_posts/` R2 테스트 객체는 필요하면 별도 관리 작업으로 일괄 삭제한다. 기능 구현의 선행 조건으로 두지 않는다.

## 11. 검증 계획

프로젝트 규칙에 따라 로컬에서는 브라우저 E2E나 라이브 서비스 테스트를 실행하지 않고 정적·구문 검사를 수행한다.

### 로컬 정적 검사

1. 수정한 모든 JavaScript 파일에 `node --check`를 실행한다.
2. 신규 mock 검사로 다음을 확인한다.
   - 프로젝트 A와 B의 게시글 목록 요청이 같은 결과를 반환한다.
   - 전역 게시글 작성에 프로젝트 ID가 필요하지 않다.
   - 댓글과 대댓글 수정·삭제가 프로젝트 공개 상태와 무관하고 비밀번호 검증은 유지된다.
   - 대댓글은 같은 게시글의 최상위 댓글에만 생성할 수 있다.
   - 다른 게시글의 댓글 또는 대댓글을 부모로 지정하면 거절된다.
   - 부모 댓글 삭제 시 하위 대댓글이 함께 삭제된다.
   - 관리자 인증 없는 작성·수정·삭제가 거절된다.
   - cursor 정렬과 대댓글을 포함한 댓글 수 집계가 유지된다.
3. migration SQL이 댓글 → 게시글 순서로 기존 테이블을 삭제하고 새 외래키·인덱스를 올바르게 생성하는지 리뷰한다.
4. 변경한 텍스트 파일이 UTF-8 without BOM이며 시작 바이트가 `EF BB BF`가 아닌지 확인한다.

### Cloudflare 배포 후 검증

사용자가 commit·push하여 Cloudflare 배포가 끝난 뒤 다음을 실제 서버에서 확인한다.

1. 프로젝트 탭 첫 화면에 프로젝트 목록과 게시글 관리 구역이 함께 보인다.
2. 프로젝트를 생성하지 않아도 전역 게시글 관리에 진입할 수 있다.
3. 프로젝트 상세에는 게시글 카드가 더 이상 없다.
4. 게시글 작성·수정·이미지 교체·이미지 제거·삭제와 관리자 댓글·대댓글 삭제가 정상 동작한다.
5. 서로 다른 두 공개 프로젝트에서 게시글 목록·상세·댓글 수가 동일하다.
6. 한 프로젝트에서 작성한 댓글과 대댓글이 다른 프로젝트의 같은 게시글 상세에 즉시 나타난다.
7. 프로젝트 이름·경로 변경 후 게시글 이미지가 정상 표시된다.
8. 프로젝트를 비공개 또는 삭제해도 전역 게시글·댓글·대댓글·이미지가 유지된다.
9. 최상위 댓글에 대댓글을 작성하고, 올바른 비밀번호로 수정·삭제할 수 있다.
10. 대댓글에 다시 답글을 달 수 없고 다른 게시글 댓글을 부모로 지정할 수 없다.
11. 부모 댓글 삭제 확인 문구가 표시되고 삭제 후 하위 대댓글도 사라진다.
12. 제거된 프로젝트별 게시글 API는 404 JSON을 반환한다.

## 12. 완료 조건

다음 조건을 모두 만족하면 전역화가 완료된 것으로 본다.

- 게시글 생성·조회·수정·삭제에 프로젝트 ID가 필요하지 않다.
- DB 게시글 행에 프로젝트 삭제 cascade가 없다.
- 모든 신규 게시글 이미지가 전역 R2 prefix에서 제공된다.
- 모든 공개 프로젝트가 같은 게시글 목록, 댓글, 대댓글을 보여 준다.
- 대댓글은 한 단계만 허용되며 부모와 같은 게시글 소속임이 서버에서 검증된다.
- 댓글과 대댓글의 비밀번호 기반 수정·삭제 및 관리자 삭제가 동작한다.
- 부모 댓글 삭제 시 하위 대댓글도 함께 삭제된다.
- 관리자 게시글 진입점은 프로젝트 탭 첫 화면에만 존재한다.
- 프로젝트 삭제·경로 변경·공개 변경이 게시글에 영향을 주지 않는다.
- 로컬 정적 검사와 UTF-8 BOM 검사를 통과한다.
- Cloudflare 배포 서버 검증을 통과한다.

## 13. 기본 결정과 추후 선택 사항

이번 계획의 기본 결정은 “하나의 전역 게시글 목록을 모든 공개 프로젝트의 게시글 탭에서 공유”하는 것이다. 다음 항목은 전역화 완료 뒤 별도 기능으로 확장할 수 있다.

- 프로젝트별로 특정 전역 글을 숨기거나 고정하는 기능
- 태그·카테고리·공지 고정 기능
- 프로젝트가 없는 독립 공개 게시글 URL
- 게시글별 공개/비공개 또는 예약 게시 기능
- 대댓글 알림 기능
- 운영 필요가 생길 경우 2단계 이상의 스레드형 댓글

이 기능들은 다시 프로젝트 소유권을 만들지 않고, 전역 게시글에 선택적 노출 규칙을 추가하는 방식으로 설계한다.
