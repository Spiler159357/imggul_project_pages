# 이미지 편집기 실사용 피드백 수정 계획

작성일: 2026-11-17  
상태: 피드백·현행 코드 대조 및 수정 계획 작성 / 구현·운영 데이터 변경 전

이 문서는 사용자의 실사용 피드백을 차기 수정 기준으로 정리한다. 기존 Photoshop 지향 계획·62개 작업 목록과 충돌하는 기능 범위·메뉴·저장 정책은 이 문서를 우선한다. 지원 이미지·문서·출력 규격은 1216×832, 1024×1024, 832×1216을 유지한다.

## 1. 수정 방향

1. 기본 화면은 새 작업 → 편집 → 작업 저장 → 이미지 내보내기 흐름에 집중한다.
2. 파일 메뉴는 **새 작업 / 작업 불러오기 / 작업 저장 / 다른 이름으로 저장** 네 가지로 구성한다.
3. 템플릿·별도 작업 복제·편집기 인페인트를 제거한다. 편집기에서 실제 제공하는 도구에는 설명을 붙인다.
4. 손가락·펜·마우스 모두 선택한 도구가 동작한다. 화면 이동은 손 도구·명시적 이동 모드·두 손가락 제스처로 구분한다.
5. 정식 작업 저장과 임시 자동저장을 분리하고, 작업 데이터 저장소는 R2로 한정한다.
6. 작업 불러오기 화면에서 위치·이름·갱신 시점·삭제를 제공한다. 버전·복구를 독립적인 파일 메뉴로 노출하지 않는다.
7. 기존 프로젝트 선택 화면의 별명·대표 이미지 규칙, 다크/라이트 색상, 모바일 색상 선택창을 일관되게 적용한다.

이번 문서 작성에서는 앱 코드·SQL migration·운영 D1·R2·브라우저 데이터를 수정하거나 삭제하지 않는다. 아래 삭제·이전 절차는 실제 수정 단계에서 수행할 작업이다.

## 2. 현재 코드에서 확인한 사실

| 확인 위치 | 코드에서 확인한 동작 | 판단 |
| --- | --- | --- |
| `public/js/editor/tools.js`의 `down()` | `pointerType === "touch"`이면 선택 도구와 관계없이 `hand`로 전환 | 손가락 편집 불가의 직접 원인 확인 |
| `engine.js` 생성자, `workspace.js`의 `entryFor()`·최초 진입 | 초기 엔진·문서가 생성되고 `stateId`와 빈 `savedId`가 달라 dirty로 시작 | 시작 화면과 실제 작업의 분리가 필요 |
| `storage.js`의 `Persistence.onChange` | 공통 `change` 이벤트와 dirty를 기준으로 2초 지연·최대 15초 자동 저장 | 보기 변경·취소/화면 이탈의 emit이 저장을 예약할 수 있음 |
| `storage.js`의 `run()`·`engine.js`의 `pack()` | 문서 자산을 PNG 인코딩·해시 계산하고 IndexedDB 복구와 원격 저장을 수행 | 네트워크 중복 업로드 방지만으로 CPU·메모리·백업 비용은 줄지 않음 |
| `src/editor/api.js` | 목록·revision·삭제 표시에 D1 사용, 출력 메타데이터 콜백도 DB에 연결 | 런타임 DDL만 제거한 상태이며 DB 사용 자체는 남아 있음 |
| `workspace.js`의 `library()`·`folderPicker()` | 별도 목록 HTML에서 폴더/파일 원본 이름을 직접 표시 | 공용 별명·대표 이미지 표시 규칙을 경유하지 않음 |
| `workspace.js`의 `notify()`·`dialog()` | 메시지는 작업 공간 상태 줄, 모달은 body에 별도 native dialog로 생성 | 모달 내부 작업의 상태 전달 경로가 필요 |
| `workspace.js`의 `renderTabs()`·`closeDocument()` | 탭에 닫기 버튼이 없고, 마지막 작업을 닫으면 다시 entry 생성 | 탭 닫기와 작업 없는 홈 상태를 함께 수정해야 함 |
| `workspace.js`의 `key()` | Ctrl/Cmd+S·C·V 등이 이미 매핑되어 있음 | 등록 여부가 아니라 포커스·공통 명령·실제 클립보드 동작을 확인해야 함 |
| `color-picker.js` | 화면 폭/기본 포인터 조건으로 모바일 선택창과 PC 기본 입력을 구분 | 다른 탭 복귀 시 회귀 원인은 재현 필요. 기기 판정·재등록·캐시까지 확인 |

펜 브러시 먹통, 탭 복귀 후 색상 UI 회귀는 사용자에게 발생한 오류로 등록한다. 코드만으로 단일 원인을 확정하거나 해결됐다고 처리하지 않는다. 새 편집기에도 PC 기본 색상 입력이 의도적으로 남아 있으므로, 원래 입력창이 보였다는 사실만으로 구 편집 모듈 호출을 확정하지 않는다.

## 4. 메뉴와 화면 흐름

### 4.1 용어와 접근 위치

현재의 저장 작업은 서버의 편집 문서를 여는 기능, 복구본은 브라우저 IndexedDB의 임시 내용을 여는 기능, 저장 버전은 과거 서버 저장 시점을 여는 기능이다. 이 세 가지를 사용자가 먼저 이해해야만 작업을 이어갈 수 있는 구성을 폐기한다. 정식 문서는 작업 불러오기로, 필요한 임시 편집은 저장하지 않은 편집 이어하기 안내로 정리하고 독립적인 과거 버전 UI는 제거한다.

| 목적 | 최종 이름·위치 | 현재 표현의 처리 |
| --- | --- | --- |
| 새 문서 생성 | 상단 **새 작업**, 홈 **새 작업** | 로컬 이미지 열기·프로젝트 이미지 등 독립 진입 버튼 통합 |
| 저장한 편집 문서 열기 | 상단/홈 **작업 불러오기** | 저장 작업 → 작업 불러오기 |
| 편집 가능한 문서 보존 | 상단 **작업 저장**, 파일 메뉴 동일 | 정식 저장 대상과 위치를 표시 |
| 현재 내용을 별도 이름으로 보존 | 파일 **다른 이름으로 저장** | 독립적인 메모리 작업 복제 명령은 제거 |
| 현재 문서에 이미지 배치 | 상단 또는 레이어 영역 **이미지 불러오기** | 이미지 레이어 추가·프로젝트 이미지 추가 통합 |
| PNG/JPEG/WebP 생성 | 상단 **이미지 내보내기** | 작업 저장과 구분하여 유지 |
| 편집 중 문서 닫기 | 작업 탭 **×** | 파일 메뉴의 작업 닫기 제거 |
| 작업 삭제 | 작업 불러오기 화면의 **삭제/선택 삭제** | 닫기와 삭제를 구분 |

규격은 **가로형 1216×832 px / 정사각형 1024×1024 px / 세로형 832×1216 px**로 표시한다. 1216×832를 16:9·HD 등 다른 표준 규격으로 부르지 않는다.

### 4.2 홈 → 생성 → 편집

홈은 문서가 아닌 화면이다. 큰 새 작업/작업 불러오기 버튼과 간단한 안내를 제공한다. 파일 드롭은 이 화면에서도 가능하다.

새 작업은 하나의 화면에서 프로젝트 이미지, 내 기기 이미지, 빈 캔버스 중 선택한다. 프로젝트 탐색·별명·대표 이미지를 같은 화면에 표시하고, 확인에 필요한 OS 파일 선택창 외에 선택 모달을 연속 중첩하지 않는다. 입력 검증·decode가 끝난 뒤 실제 문서를 생성한다. 잘못된 규격·취소·실패는 빈 탭을 남기지 않는다.

이미지를 넣을 때는 현재 문서의 **이미지 불러오기**를 사용한다. 모달은 새 작업 생성인지 현재 작업에 배치하는지 제목과 설명으로 구분한다. 두 흐름은 같은 프로젝트 이미지 선택 컴포넌트를 사용한다.

### 4.3 정식 저장·불러오기·닫기

첫 작업 저장에서 작업 이름과 저장할 프로젝트를 확인한다. 위치는 예를 들어 **프로젝트 A / 편집 작업 / 캐릭터 보정**으로 표시한다. 이후 저장은 같은 작업을 갱신한다. R2 내부 경로는 필요 시 상세 정보로 확인할 수 있게 하되 원시 키만으로 저장 위치를 설명하지 않는다.

다른 이름으로 저장은 새 문서 ID·정식 저장본을 생성하고 현재 탭을 그 저장본으로 전환한다. 기존 정식 작업은 유지한다. 별도 임시 복제 탭을 늘리는 동작으로 구현하지 않는다.

작업 불러오기는 정식 작업 목록·이름·썸네일·저장 시점·프로젝트/위치·삭제를 제공한다. 임시 편집이 남아 있으면 별도 복구본 메뉴 대신 **저장하지 않은 편집 이어하기 / 삭제**라는 목적이 드러나는 안내를 제공한다.

탭 ×는 내용 변경이 없으면 바로 닫는다. 정식 저장에 반영하지 않은 변경이 있으면 작업 저장/저장하지 않고 닫기/취소를 제공한다. 명시적으로 저장하지 않고 닫기를 선택하면 해당 임시 편집도 폐기한다. 마지막 탭을 닫으면 문서 없는 홈으로 돌아간다. 작업 삭제는 정식 저장본과 대응하는 임시본·전용 자산을 삭제하는 별도 동작이다.

## 5. 자동 저장과 최적화

### 5.1 상태와 트리거

내용 상태, 마지막 정식 저장 상태, 마지막 임시 저장 상태를 분리한다. 자동 저장에 성공해도 정식 작업 저장이 끝난 것으로 표시하지 않는다. 상태 문구는 미저장 변경 / 임시 저장됨·작업 저장 필요 / 작업 저장됨 / 저장 실패로 구분한다.

| 이벤트 | 처리 |
| --- | --- |
| 홈 진입·새로고침·탭 재진입 | 작업 생성·저장 없음 |
| 초기 빈 캔버스/원본 열기 | 초기 문서 상태로 취급. 편집이 없으면 자동 저장 없음. 명시적 작업 저장은 가능 |
| 획 완료·레이어/텍스트/마스크 변경 확정 | 내용 변경 이벤트, 임시 자동저장 예약 |
| Undo/Redo | 내용 상태 변경이므로 같은 경로로 예약. 정식 상태로 돌아오면 오래된 임시본도 정리 |
| 도구·레이어 선택·줌·pan·패널·후보 없는 단순 화면 갱신 | 저장 없음 |
| 변형·슬라이더·획 진행 중 | 미확정 내용 저장 없음 |
| 편집기 문서 탭 전환·다른 앱 탭/화면으로 이동 | 변경된 내용의 대기 임시 저장만 처리. 이미 저장한 상태면 요청 없음 |
| 페이지 hidden·브라우저 이탈 | 준비된 최신 임시 저장을 최선 노력으로 전송. 같은 상태를 중복 전송하지 않음 |

`document:changed`와 `view:changed`를 구분하고 자동 저장은 전자에만 연결한다. 매 이력의 모든 중간 상태를 원격에 저장하지 않고, **마지막 편집 확정 후 5초 대기해 연속 변경을 병합하는 안**을 기본 제안으로 둔다. 주기적인 무조건 저장·폴링은 두지 않는다. 화면 이탈 전에는 준비된 변경을 우선 처리한다.

브라우저 종료 순간 비동기 업로드 완료는 보장할 수 없다. 편집 확정 시점부터 미리 저장 준비를 해두고 `visibilitychange`의 hidden 등에서 전송 기회를 확보한다. 오프라인·미전송 상태는 숨기지 않고 표시한다. 무거운 종료 시 전체 인코딩에 의존하지 않는다. [MDN의 페이지 가시성 설명](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)을 기준으로 구현한다.

### 5.2 임시 공간과 비용

아래 값은 구현 전 조정 가능한 초기 제안이며 현재 적용된 제한이 아니다.

| 항목 | 제안 |
| --- | --- |
| 임시 작업 개수 | 프로젝트당 최대 10개 |
| 임시 데이터 용량 | 프로젝트당 총 256MiB. 미완료 업로드도 포함 |
| 보관 기간 | 마지막 사용 후 7일 |
| 작업당 임시본 | 완료된 최신 상태 1개와 전송 중 상태만 유지. 편집마다 버전 누적 금지 |
| 요청 | 문서당 진행 중 저장 1개 + 교체 가능한 최신 대기 상태 1개 |

이미 저장한 자산은 자산 ID·변경 버전별 PNG/해시 캐시를 재사용한다. 변경하지 않은 원본·이미지·마스크를 매번 인코딩하지 않는다. 변경 자산만 업로드하고 manifest는 확정된 상태로 교체한다. 일반 브러시에 필요하지 않은 전체 합성 샘플 생성도 분리해 긴 획의 지연을 줄인다.

자동 저장이 정식 저장 폴더·정식 목록·정식 저장 시점을 갱신해서는 안 된다. 정식 저장 성공 후 불필요한 임시본을 정리한다. 임시 저장 상한 초과는 서버의 예산 예약/정산과 정리로 통제하며, 다른 사용 중 작업을 조용히 삭제하지 않는다. 삭제 가능한 오래된 임시본이 없으면 실패와 정리 방법을 표시한다.

R2 lifecycle은 임시 경로의 만료 정리를 보조한다. 삭제가 비동기로 진행되므로 lifecycle만으로 즉각적인 용량 상한을 보장하지 않는다. [Cloudflare lifecycle 동작](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)과 별개로 서버 상한을 구현한다.

IndexedDB에 문서·PNG를 중복 보관하는 영구 복구 저장은 제거한다. 작업·백업은 R2를 사용한다. 최근 색상·패널 배치 같은 소량의 UI 설정은 작업 문서 저장과 구분한다. 네트워크 단절·강제 종료 시 잃을 수 있는 마지막 변경을 무거운 복구 시스템으로 숨기지 않는다.

## 6. R2 전용 저장과 DB 제거

### 6.1 저장 구조

이번 규모와 기능에는 편집 작업 저장을 위해 D1을 유지할 필요가 없다. 목록은 R2 manifest 객체의 작은 customMetadata로 제공하고, 저장 충돌은 객체 ETag 조건부 갱신으로 처리한다. 목록에는 cursor/truncated를 적용하고 첫 페이지를 전체 목록으로 오인하지 않는다. 별도의 DB나 전역 JSON 인덱스와 문서 사이 이중 commit을 도입하지 않는다. 해당 기능은 [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)를 기준으로 설계한다.

```text
__editor/v2/{projectId}/
  saved/documents/{documentId}.json      정식 문서 manifest + 목록용 metadata
  saved/assets/{documentId}/{hash}.png  해당 작업 전용 자산
  saved/previews/{documentId}/…          정식 작업 썸네일
  autosave/{sessionId}/{documentId}/…    최신 임시 편집과 그 자산
```

정식 저장은 자산 준비 → ETag 조건부 manifest 확정 순서로 한다. 실패한 업로드가 기존 정식 문서를 망가뜨리지 않게 하고, 확정 후 참조되지 않는 해당 문서 자산을 정리한다. 진행 중 저장과 최신 manifest 참조를 확인한다. 문서별 자산 소유를 명확히 해 다른 문서가 사용하는 전역 공유 파일을 오삭제하지 않는다.

### 6.2 직접·간접 DB 의존성

- 편집 전용 API에 `env.DB`를 전달하지 않고 R2 capability만 전달한다. SQL·스키마 확인·revision 영수증·DB 목록·DB 삭제 표시를 제거한다.
- `functions/[[path]].js`에서 편집기에 주입하는 `readFileMetadata`/`putFileMetadataForKey`의 DB 콜백을 제거한다. 출력·원본 연결 정보도 R2 metadata 또는 편집 전용 R2 sidecar로 보관한다.
- 프로젝트 갤러리의 편집 결과 표시가 기존 `file_metadata`만 읽고 있다면 R2 측 정보도 읽을 수 있도록 함께 연결한다. 저장 성공 뒤 결과 정보가 누락되는 상태를 방치하지 않는다.
- 별명·캐릭터 정보는 호스트 프로젝트 화면에서 이미 읽은 공용 표시 모델을 전달받아 사용한다. 편집기 전용 저장/목록 구현이 별명 조회를 명분으로 DB 의존성을 다시 갖지 않게 한다.
- 공용 프로젝트·캐릭터·별명 서비스 자체의 기존 DB는 편집기 데이터가 아니다. 이를 편집기 정리 migration으로 삭제하지 않는다. 공용 정보 조회의 데이터 출처와 편집기 자체의 추가 DB 요청 유무를 감사 기록에 남긴다.
- 작업 데이터·복구·템플릿을 담던 브라우저 IndexedDB도 제거 대상으로 포함한다. 편집기 내부 AI를 제거해 후보/요청 스냅샷 저장 의존성도 없앤다.
- 운영 스키마 정리는 별도 migration으로만 한다. HTTP 요청에서 CREATE/DROP/ALTER 또는 자동 migration을 실행하지 않는다.

DB가 필요해지는 기능이 새로 제안되면 목적·R2만으로 불가능한 점·비용을 먼저 설명한다. 이번 수정에는 그런 예외를 두지 않는다.

## 7. 기존 데이터와 migration 정리

사용자가 편집기 데이터 보존이 불필요하다고 명시했으므로 구 편집 문서를 새 구조로 이전하지 않는다. **전용 데이터 초기화 후 새 구조로 시작**한다. 다만 공용 프로젝트 원본·캐릭터·별명·인증 데이터는 편집기 데이터와 구분한다.

| 구분 | 실제 수정 시 처리 |
| --- | --- |
| D1 `editor_workspace_documents`, `editor_workspace_revisions` | 다음 신규 정리 migration에서 삭제. 현재 마지막 migration이 0027이므로 예시 파일명은 `0028_remove_editor_workspace.sql` |
| 구 `image_editor_documents`, `image_editor_revisions` | 실제 존재·전용 소유 확인 후 같은 정리 범위에 포함 |
| 공용 `file_metadata`, 프로젝트·캐릭터·별명 테이블 | 테이블 삭제 금지. 편집기 테스트 결과 행이 식별될 때 그 행만 선택적으로 정리 |
| R2 `__editor/`, `__editor_sessions/`, `__editor_backups/` 등 | 실제 존재하는 편집 전용 객체를 목록화해 정리. 새 v2 생성 전 수행하거나 v2를 명시적으로 제외 |
| 프로젝트 폴더의 편집기 테스트 출력 | 출력 기록·editorDocumentId 등으로 식별한 대상만 목록화. 원본 sourceKey·공용 이미지와 구분해 처리 |
| 브라우저 `imggul-editor-workspace` IndexedDB | 구 복구·템플릿 데이터를 포함해 제거 |
| 메모리 세션·구 설정·리소스 캐시 | 세션 초기화·자산 버전 전환. 전역 테마·로그인 정보는 정리 대상에서 제외 |

이미 적용된 0027 파일을 과거에 없었던 것으로 바꾸지 않는다. 앞으로 적용할 정리 migration을 추가해 최종 상태가 편집기 DB 테이블 없음이 되게 한다. 신규 설치의 전체 migration 적용 결과도 동일하게 확인한다.

작업 삭제 기능은 단순한 deleted 표시로 끝내지 않는다. manifest·썸네일·전용 자산·임시본까지 정리하고 요청 재시도는 안전하게 처리한다. 삭제 전에 대기 저장을 끊고, 오래된 탭의 늦은 요청이 삭제한 작업을 재생성하지 못하도록 문서/세션 세대와 존재/ETag 조건을 확인한다. 원본 이미지와의 참조 관계는 삭제 대상 소유권으로 취급하지 않는다.

전환 순서는 **새 코드 준비 → 구 편집기 쓰기 중지 → 대상 목록/건수 확인 → 전용 DB/R2/브라우저 데이터 정리 → R2 전용 코드 배포·활성화 → 검증**이다. 구 캐시 클라이언트는 새 프로토콜에서 거부해 재접속을 안내한다. 운영 데이터 정리는 끝날 때까지 재실행 가능한 작업 기록을 남긴다.

## 8. 입력·공통 UI·안내·단축키

### 8.1 모바일·펜

한 손가락은 선택 도구를 실행한다. 이동(V)은 레이어 위치 변경, 손(H)은 화면 이동이다. 두 손가락은 pan/zoom으로 구분하고, 두 번째 손가락이 들어오면 진행 중인 미확정 획을 정리해 점이 남지 않게 한다.

펜의 pointerdown/move/up·capture·cancel과 압력 0·미지원 장치를 각각 확인한다. 미지원 압력은 기본 강도로 동작하고, 펜 사용 중 손바닥 입력은 별도 처리한다. 마스크/벡터 대상·빈 선택·잠금·0 불투명도 등 편집이 제한된 원인도 읽을 수 있게 표시한다. 도장 기준점 등 Alt 조작은 모바일에서 명시적인 샘플 선택 버튼으로 접근할 수 있어야 한다.

### 8.2 별명과 썸네일

`selection-ui.js`·`asset-picker-cards.js`와 프로젝트 표시 데이터를 기준으로 공통화한다. `getSelectionFolderImage()`·`getSelectionFileAlias()`가 편집기의 사용 문맥에서도 같은 규칙을 지키는지 확인한다. 캐릭터 대표는 0번 이미지 규칙을 따르며, 0번 이미지가 없거나 로드 실패하면 명확한 자리표시자를 사용한다. 임의의 다른 이미지를 대표로 선택하지 않는다.

이름·별명·원래 파일명 검색, 계층 이동, 현재 위치, 누락 이미지, 공개 범위와 URL 인코딩을 함께 확인한다. 폴더마다 전체 이미지 목록을 추가 요청하는 N+1 조회를 만들지 않는다.

### 8.3 모달·메뉴·색상

모달에 제목·작업 목적·진행 상태·오류·재시도·닫기를 제공한다. 각 동작은 모달의 상태 영역에 메시지를 보내고 실행 중 버튼 상태를 표시한다. native dialog의 top layer 바깥 toast에 z-index만 높이는 방식으로 해결하지 않는다. 중첩 모달에서도 현재 수행한 작업의 메시지를 읽을 수 있어야 한다.

메뉴는 바깥 pointer 입력·다른 메뉴·명령 실행·Esc에서 닫고 리스너는 화면 이탈 시 해제한다. 작업 탭의 ×는 탭 선택 버튼과 분리하여 버튼 안에 버튼을 중첩하지 않는다.

색상은 동일한 컨트롤을 재사용한다. 실제 터치 입력·펜/마우스·viewport 변경을 함께 고려하고, 다른 탭 복귀 시 컨트롤·리스너를 다시 연결한다. 관련 JS/CSS/import의 자산 버전을 일관되게 갱신해 구·신 UI 혼합을 방지한다. PC 기본 입력과 모바일 하단 선택창 각각의 회귀 시나리오를 확인한다.

### 8.4 PC 단축키

| 키 | 동작 |
| --- | --- |
| Ctrl/Cmd+S | 작업 저장. 새 문서는 이름/위치 지정 |
| Ctrl/Cmd+Shift+S | 다른 이름으로 저장 |
| Ctrl/Cmd+O | 작업 불러오기 |
| Ctrl/Cmd+Z, Shift+Z, Ctrl+Y | 실행 취소/다시 실행 |
| Ctrl/Cmd+C, X, V | 캔버스에서는 선택 내용 복사/잘라내기/붙여넣기, 텍스트 입력 중에는 브라우저 기본 동작 |
| Ctrl/Cmd+A, D, J | 전체 선택, 선택 해제, 레이어 복제 |
| Delete, Space, V/B/E/M/T, [ / ] | 대상 삭제, 임시 손 도구, 주요 도구, 브러시 크기 |

현재 내부 clipboard 변수만 갱신하는 복사와 OS 이미지 클립보드를 구분한다. 붙여넣기 keydown과 paste 이벤트가 충돌하거나 두 번 실행되지 않게 한다. OS 클립보드 접근이 제한되면 사용자에게 결과와 대체 동작을 알린다. [Clipboard API의 이미지 읽기·권한 조건](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/read)을 확인한다.

편집기 활성 상태·입력 포커스·IME·모달을 명령 라우터에서 구분한다. 편집기 안에서 이름/속성을 편집 중이어도 저장 키는 확정 가능한 입력을 처리한 뒤 작업 저장으로 연결한다. 텍스트 복사/붙여넣기는 가로채지 않는다. 브라우저 예약 키를 모든 환경에서 강제로 재정의할 수 있다고 가정하지 않는다.

## 10. 배포 검증 시나리오

로컬은 저장소 규칙에 따라 구문·정적 검사만 수행한다. 사용자가 commit/push한 Cloudflare 배포에서 실제 동작을 검증한다.

1. 홈 진입·새로고침·다른 탭 왕복·마지막 탭 닫기를 반복해 문서/저장 요청/R2 객체가 증가하지 않는지 확인한다.
2. 파일 선택 취소·decode 실패·지원 밖 규격에서 빈 작업이 남지 않는지 확인한다.
3. 세 규격 각각 새 작업 → 손가락/펜/마우스 편집 → 작업 저장 → 불러오기 → 이미지 내보내기를 수행한다.
4. 도구·선택·pan/zoom·패널 변경만 반복했을 때 저장 요청이 0건인지 확인한다. 한 획 도중 저장/전체 인코딩이 실행되지 않는지도 기록한다.
5. 연속 편집의 저장 병합·탭 이탈·hidden·오프라인·종료를 확인하고 자동저장과 정식 저장의 위치·상태·목록이 분리되는지 확인한다.
6. 같은 작업 두 창 충돌·저장 중 새 편집·실패/재시도·다른 이름 저장·작업 삭제/늦은 응답·용량 상한·기간 만료·미완료 파일 정리를 확인한다.
7. 모달을 닫지 않고 오류·진행·재시도를 읽을 수 있는지, 별명 검색·캐릭터 0번 이미지·폴더 이동이 공통 화면과 같은지 확인한다.
8. 색상 선택의 탭 왕복·작업 전환·재마운트·회전·새로고침·다크/라이트·중첩 모달을 확인한다.
9. 단축키를 캔버스·작업명·문자 내용·모달·IME·외부 이미지 클립보드에서 각각 확인한다.
10. 편집기 전용 DB 테이블/SQL/콜백과 인페인트·템플릿 실행 의존성이 없는지 정적으로 확인하고, 실제 편집 저장 과정의 서비스 호출도 대조한다. 이미지 생성 탭·기존 프로젝트 기능은 별도로 회귀 확인한다.
11. 대표 문서의 획 반영 시간·인코딩 횟수·네트워크 요청/전송량·임시 총용량을 수정 전후 같은 기기에서 비교한다. 측정 전 최적화 완료를 선언하지 않는다.

계획 작성 시점에는 모든 항목이 구현/검증 대기다. 사용자의 실사용 재현 결과와 소스에서 확인한 사실은 구분해 위 표에 반영했다.
